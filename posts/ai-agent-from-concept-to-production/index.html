AI 时代漫游：Agent 从概念到工程

大部分人接触 AI，都是从聊天类应用开始的。我们比较习惯一问一答的方式，让它来查资料、润色下文案，但对话和问答只是 AI 能力的一小部分。相比于“聊天”类的 AI 应用，Agent（智能体）的核心价值在于能够帮你“做事”，不只是一个问答者，而是能直接帮你发送邮件、修改文件的执行者。

什么是 Agent？

Agent 是一个能感知环境，进行思考推理，并采取行动以完成特定目标的数字实体。

跟传统的软件对比：

  • 传统软件是“过程驱动”的：依赖于预设的固定步骤执行逻辑，按部就班地执行指令编码。
  • 智能体是“目标驱动”的：具有高度的自主性和灵活性，能根据实时环境动态规划实现路径。

通常 Agent 的架构由以下几个部分组成：

  • 大脑（LLM）：负责理解用户意图，推理与决策。
  • 规划（Plan）：把大的目标拆解为更小的目标。
  • 记忆（Memory）：包括短期记忆（对话上下文）与长期记忆（用户行为等）。
  • 工具（Tools）：大模型可以使用的外部能力，如 API、搜索引擎、数据库等。

Agent 核心历史节点

2022 年 10 月，普林斯顿大学和 Google Brain 联合发表了里程碑式论文《ReAct: Synergizing Reasoning and Acting in Language Models》，奠定了现代 Agent 的底层思维范式。通过将思考（Reasoning）和行动（Acting）结合，ReAct 让大模型能够动态规划路径，并主动调用外部工具，这种“边想边做”，通过外部环境的结果不断调整计划的方式，极大提升了任务完成质量，显著降低了大模型幻觉。

在 2023 年初，火爆的 AutoGPT，则是现代 Agent 的工程奠基者。它将 LLM（大脑）、向量数据库（长期记忆）、Python 解释器（工具）、无限任务循环封装在了一起，划定了现代 Agent 的基本框架 —— 大脑、记忆、工具、规划。后续 OpenAI 的 《LLM Powered Autonomous Agents》 将这一套工程实践，确立为行业公认的 Agent 标准，统一了行业的术语和架构认知。

Agent 主流设计模式

Agent 的设计模式，不同于编程里传统的设计模式（单例模式、工厂模式等）。传统的设计模式处理的是代码逻辑和对象结构，而 Agent 的设计模式更像是认知流程和团队协作的描述。

它本质是对人类如何做事（规划、反思、工具使用）和团队协作（流水线、分派、辩论）的抽象和工程复刻。明白了这一点，你就明白 Agent 框架的核心不在于代码的复杂性，而是其工作流设计得是否符合人类高效做事的实践。

吴恩达提出的 Agent 原子能力，关注 Agent 底层思考与行为模式：

  • Reflection（自我反思）： 模型评估自身输出结果，进行多轮自我纠错与迭代改进。
  • Tool Use（工具调用）： 模型根据上下文，动态决定何时以及如何调用外部 API（搜索、代码执行、数据库查询等）。
  • Planning（动态规划）： 模型将复杂大目标拆解为子步骤，并按顺序或树状结构探索执行。
  • Multi-Agent Collaboration（多智能体协作）： 多个 Agent 扮演不同角色，通过分工、讨论与辩论共同完成任务。

Anthropic 提出的工程设计模式，关注任务处理流程：

  • 工作流模式（Workflows）
    • Prompt Chaining（流水线）：串行地完成任务，上一个步骤的输出作为下一个步骤的输入。
    • Routing（路由）：用小模型完成分类，将任务分配给对应的专门的 LLM 执行。
    • Parallelization（并行化）：多个独立的子步骤可以并发的执行，最后进行汇总。
    • Orchestrator-Workers（编排者-工作者）：一个 LLM 拆解任务后，分配给多个 worker 并发执行后汇总。
    • Evaluator-Optimizer（评估者-优化者）：一个 LLM 处理，另一个 LLM 进行评估，反复循环处理直到符合预期。
  • 自主智能体模式（Autonomous Agents）
    • Agent Loop（自主循环）： 代码仅提供工具集与目标，由 LLM 在运行期自行决定下一步做什么、何时调用工具、何时终止。流程非代码预设，适应性极强，但控制力与稳定性较弱。

Agent 工程落地

Agent 在 Demo 中看起来无所不能，但真要落地到生产环境，需要解决的是“大模型的概率性和不确定性”与真实业务对“高可靠、低延时、可控”的要求之间的矛盾。

在生产落地，主要有以下方面的挑战：

  • 确定性与可控性：幻觉在长链路中放大，模型容易陷入死循环或多次结果不一致。
  • 性能与成本：动态多轮循环带来的高延迟，且上下文不断膨胀导致 Token 成本失控。
  • 安全性：大模型可能会被提示词注入攻击，且模型动态调用工具容易发生越权。
  • 可观测性和评估：缺乏 Tracing 导致黑盒排查难，模型效果缺乏评估体系。
  • 状态与记忆退化：随着上下文变长，模型注意力被稀释与记忆检索噪声干扰。

针对这些挑战，工程落地的核心思想是：用确定性的工程代码，给不确定性的 LLM 搭建基础设施与护栏。业内流行的 Harness 工程，就是这套大模型之外的完整工程解决方案，主要包括：

  • 流程控制：限制最大步数、错误回退、超时中断等，防止死循环和错误级联。
  • 环境隔离：提供沙箱环境，控制 API 权限，防止高危操作。
  • 安全护栏：对输入（提示词注入）和输出（格式和合规）进行校验。
  • 状态与评测：实现全链路 Tracing 来方便排查，自动化运行 Evals 测试集衡量模型表现。

Demo 追求的是 Agent 的上限，能够做什么，而工程落地则更看重错误下限，它在最坏情况下会怎样。决定一个 Agent 能否真正落地的，往往不是大模型的智商上限，而是包裹在外层的工程 Harness 是否足够坚固 —— 用确定性的软件工程，驯服不确定性的 AI 引擎。
